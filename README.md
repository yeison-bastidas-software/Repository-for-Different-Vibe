# Different Vibe
#### Video Demo: https://youtube.com/shorts/-K4qxseJcuM
#### Description:
Different Vibe is a full-stack web application designed to modify the playback speed and pitch of audio files through an intuitive, user-friendly interface. Built for the CS50x Final Project, it allows users to upload MP3 or WAV files, select between two distinct audio transformation modes (Slow or Speed), and adjust the intensity of the effect using a dynamic slider ranging from 0% to 100%. The application processes the audio server-side, provides real-time progress feedback based on file size, and delivers a downloadable, transformed audio file. Additionally, every processing session is logged in a local SQLite database, creating a persistent history of user interactions for potential future features like user accounts or analytics.

The project is structured following standard Flask conventions, separating backend logic, frontend templates, static assets, and helper functions to ensure maintainability and scalability. Below is a detailed breakdown of each component and the design decisions behind them:

`app.py` serves as the application's entry point and route controller. It initializes the Flask instance, configures secret keys and upload directories, and establishes the SQLite database connection using the CS50 SQL wrapper. The file defines five core routes: `/` handles file uploads with secure UUID-based renaming to prevent filename collisions and overwrite issues; `/choose` presents the mode selection interface; `/edit` renders the intensity slider and calculates file size for progress estimation; `/process` orchestrates the audio transformation by calling the helper function, logging the transaction to the database, and redirecting to the results page; and `/result` displays the final audio player with download capabilities. Session management is used throughout to securely pass the uploaded filename between routes without exposing it in URLs.

`helpers.py` contains the core audio processing logic. Initially, I attempted to use Pydub’s built-in `speedup()` function for the Speed mode, but encountered inconsistent behavior and crashes with certain MP3 codecs. After debugging, I pivoted to a more robust technique: frame-rate override. By manipulating the audio segment’s sample rate (`frame_rate`) proportional to the desired speed factor, and then re-exporting it at the standard 44,100 Hz, the application naturally shifts both tempo and pitch simultaneously. This method proved significantly more stable, produced cleaner audio without artifacts, and allowed both Slow (0.7x–1.0x) and Speed (1.0x–1.5x) modes to share the same underlying algorithm, reducing code duplication. The function returns a boolean success flag, allowing `app.py` to handle errors gracefully.

The `templates/` directory contains five Jinja2 HTML files that structure the user interface. `layout.html` acts as the base template, loading Bootstrap 5, custom CSS, and JavaScript while providing a consistent navigation bar. `index.html` focuses on a clean, distraction-free upload experience with a custom-styled file input. `choose.html` uses interactive cards to clearly differentiate between the Slow and Speed modes. `edit.html` implements the intensity slider, progress bar, and embeds the JavaScript logic directly to avoid browser caching issues that previously caused mode selection bugs. `result.html` renders the HTML5 audio player and download button. All templates are responsive and designed with a dark theme to reduce eye strain and emphasize the audio controls.

The `static/` directory holds `style.css` and `script.js`. The CSS file defines the dark color palette, custom button gradients, card hover effects, and progress bar animations that visually distinguish between the Slow (blue) and Speed (green) modes. The JavaScript file handles UI interactions, such as updating the file name display on upload and synchronizing the slider value with the intensity percentage. I made the deliberate choice to keep the progress simulation logic inside `edit.html` rather than `script.js` to ensure the correct mode variable is always passed to the backend, eliminating a persistent caching bug during development.

`requirements.txt` lists the Python dependencies (`flask`, `pydub`, `cs50`), ensuring reproducible environment setup. FFmpeg is required system-wide for Pydub to function, as noted in the installation instructions.

During development, I faced several challenges that shaped the final architecture. The most significant was the browser caching issue where JavaScript would consistently send "slow" mode regardless of user selection. By embedding the mode variable directly in the HTML template and removing external script dependencies for that specific logic, the issue was resolved. Another key decision was using UUIDs for uploaded filenames. This prevents security vulnerabilities, avoids overwriting existing files, and ensures the application can handle concurrent users safely. The SQLite database was implemented not just to meet course requirements, but to establish a foundation for future features like user authentication, processing history dashboards, and rate limiting.

Different Vibe demonstrates a complete web development lifecycle: secure file handling, server-side audio manipulation, dynamic frontend interactions, database integration, and responsive design. It balances technical complexity with user experience, providing a reliable tool for content creators, DJs, and casual listeners who want to experiment with audio tempo and pitch transformations.
